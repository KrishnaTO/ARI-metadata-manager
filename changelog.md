# Changelog

## ref-edits-topbar-redesign
- **Rebuilt the `/ref-edits/` toolbar as a single 48px row.** It held 14 sibling controls at one level of emphasis and wrapped to **three rows / 161px** at a 1440×900 window — ~18% of the viewport spent on chrome above a matrix that is itself the work. Measured in the running app: content needed ~1950px of track against 1152 available (the page renders at `--ui-zoom:1.25`, so a 1440px screen is 1152 layout px).
- The row now reads in three zones, separated by hairlines rather than gaps: **identity** (back arrow, title) · **scope** — what the matrix shows (filter, queue segment) · **status and action** (progress, pending, ⚗, ⚙, user, Publish). Nothing was deleted; the count of visible controls fell from 14 to 9 because the set-and-forget ones moved.
- **Theme, row density and the glyph legend became preferences behind ⚙.** They are decided once and never touched again during a review, so they were paying permanent toolbar rent — 322px of it. Both segmented controls keep their ids, markup and handlers; only their location changed. The legend is new as an option: it is a fixed footer of reference text, now hideable (`html[data-legend]`, persisted as `refLegend`) once a curator knows the glyphs, which returns a further 30px to the matrix.
- **Publish became a split button.** `Publish review (PR)` + `New PR` + the bare `PR #128 ↗` link were three peers competing with the primary action; the caret — which only appears once a PR is on file — now holds "Open PR #128 ↗" and "Publish to a new PR". `reflectPr()` toggles one `has-pr` class instead of three inline `display` strings.
- Smaller trims: the back button is an icon (was a 133px labelled button), the progress meter reads `12/210 reviewed` with a 64px bar (was 354px of prose), the enrichment chip is the ⚗ icon with its explanation on the tooltip, and the queue segment reads "Mine" rather than "My queue".
- **The toolbar never wraps.** Under pressure the filter shrinks to 118px, then three pieces step out in order of how little they carry — the progress caption, the page title, the meter itself. No *control* is ever hidden. The thresholds are written in device pixels and sit 25% above the layout widths they guard, because `zoom` does not apply to media queries.
- Accessibility and polish, none of which the old bar had: `:focus-visible` rings across the toolbar and its popovers, `aria-expanded` on every toggle (drawers included, via the new `reflectDrawer()`), `aria-label` on the icon-only buttons, and a pressed state so an open drawer is visible on its chip. The status dots now appear only when they mean something instead of sitting grey.
- Popovers close on outside click and on Escape, and only one is open at a time.
- Verified in the running app at 1440/1280/1100px: one 48px row with zero overflow in the widest state (signed in, queue segment shown, "Publish to PR #128" + caret), every toolbar item centred on the same axis, all buttons a uniform 28px. Preferences round-trip through `localStorage`, the density change re-lays the grid to `250px repeat(10, …)`, and the drawers, the split menu and Escape all behave. No console errors; page tests pass.

## fix-feedback-store-eager-mkdir
- Fixed `OntologyService` failing, or silently degrading, whenever it is built over an ontology outside the app tree. `FeedbackStore.__init__` created its directory eagerly, and the store's path is derived from the ontology file's **grandparent** — so a service over a downloaded ontology in the system temp directory tried to `mkdir /feedback` and raised `PermissionError` on Linux. The store now creates its directory on first write instead; reading never touches the disk.
- Found by `scripts/backfill_id_authors.py` crashing on the production host. It was invisible on Windows, where the temp directory is nested deep enough (`…/AppData/Local/Temp/x.owl`) that the grandparent is writable — on Linux `/tmp/x.owl` makes it `/`.
- **Two production paths had been failing silently the whole time**, both wrapped in `except Exception`: the publish change summary ([app/main.py:735](app/main.py:735)), so every PR body opened from the live server read "_Change summary unavailable (could not load the source-branch baseline)._", and the signed-in export baseline ([app/main.py:885](app/main.py:885)), so exports lost their changed-cell marking. Neither is a new regression — they have behaved this way on Linux since those temp-file baselines were introduced. Both are fixed by this one change; no call site needed editing.
- Regression test builds a service over an ontology whose grandparent must not be written to and asserts no sibling directory appears. `test_feedback_store_survives_corrupt_json` now creates the directory itself, since it seeds a corrupt file directly rather than going through the store's API.

## ref-edits-mapping-confirmation
- **A curator can no longer confirm a cross-reference id they added themselves** (`/ref-edits/`). Adding an id and confirming it were previously one person's unchecked act, so a mapping could enter the SSSOM files on a single curator's say-so; a second curator now has to vouch for every match. Only the ✓ is withheld — the same curator may still flag their id as wrong, or declare the database empty.
- Authorship is recorded server-side, since it has to outlive the adding curator's own session and private working copy. New `app/id_provenance.py` keeps `provenance/id-authors.json` (`"<iri>|<db>|<id>" -> {login, at}`, gitignored runtime state like `assignments/`), written by `PUT /api/v2/disease/{iri}` and `POST /api/v2/disease` from a before/after diff of the disease's cross-references — so *any* path that introduces an id is covered, not just the review page. Only an id's **first** author is kept, so removing and re-entering an id cannot be used to take it over. `GET /api/v2/id-authors` serves the map.
- The rule is enforced at both ends. The page marks each id with "added by @login", strikes through the ✓ on your own, and answers an attempt to click it with a note bar saying why and what you can do instead; `POST /api/v2/publish` independently rejects a `confirmed` entry whose id the caller added, so a stale or hand-made request cannot slip past the UI. A failed `id-authors` fetch only relaxes the frontend hint — the server check still holds.
- New `OntologyService.get_xrefs(iri)` reads one disease's ids by database; the edit endpoints call it either side of the write rather than rebuilding the full `get_disease_detail()`.
- **Added a "∅ Not in *DB*"** verdict for cells with no id on file, on both the review-strip card and the side panel (issue: a database that genuinely has no term for a disease was indistinguishable from one nobody had looked at, and such a cell could never be cleared). It is a per-cell judgment, not per-id: it publishes as an SSSOM row against `sssom:NoTermFound` with the database in a new `object_source` column, and as `manual-absent` in the equivalencies file. Cells marked this way count as complete, show `∅` in the matrix, and are skipped by "Next open mapping". `predicate_modifier` is left empty — `NoTermFound` is a recorded absence, not a negative mapping.
- Fixed `_merge_tsv` mangling rows written under an **older header**. It only skipped a header line that matched the current columns exactly, so after `predicate_modifier` was added (and now `object_source`), the stored file's own header was re-merged as if it were data and every stored row was written one column to the left of where it belonged. Rows are now re-mapped by column name through the header they were written under, and a legacy row missing `object_source` has it backfilled from its object CURIE — without which every historical mapping in `mappings/ari.sssom.tsv` would have been duplicated on the next publish, since `object_source` is part of the dedup key (two databases share the `NoTermFound` object).
- Disease changelogs record the new verdict too: `log_xref_review` takes `absent` and appends "no term in MONDO" alongside the existing confirmed/flagged entries.
- **Backfilled the ledger from the curated mappings** (`scripts/backfill_id_authors.py`), so the rule also covers work done before the ledger existed rather than only new edits. Both files name a curator per mapping — SSSOM `author_id`, equivalencies `source` — and the script resolves `ARI:00NNNNN` → disease IRI through the ontology and the object CURIE prefix → review column. **359 ids: @KrishnaTO 262, @AnjaliRH 63, @Jennyzeng25 34.** Run once per deployment; re-running is safe because an id keeps its first author.
  - Reads the mappings **and the ontology** from the source ARI repo (`KrishnaTO/ARI@main`) — where `POST /api/v2/publish` actually accumulates them — over public `raw.githubusercontent.com`, so no token or `gh` is needed on the server. This repo's tracked copies are a stale snapshot: its `mappings/` hold 45 rows against the source's 443, and its ontology resolves 245 of the 322 curated mappings against 310 for the source repo's. `--local` reads the working tree instead.
  - Both files are read because **neither is a superset of the other** — 3 mappings appear only in each, always the same mapping with the id written differently (ICD-10 `362.5`/`362.50`, DOID `111157`/`0111157`, ICD-10 `720`/`720.0`). No reconciliation is needed: a mapping is recorded only while its id is still on file, so whichever spelling the ontology carries wins and its twin is skipped. A mapping present in both files is recorded once.
  - Only **positive** rows are used: a negative (SSSOM `Not`, equivalencies `manual-negative`) names whoever *flagged* a mapping and a `NoTermFound` row has no id, so neither says who added anything — 248 rows skipped on that basis. Non-`github:` authors are skipped, an ORCID being unresolvable to the login the lock compares against.
  - 12 distinct mappings resolve to no id on file and are left unattributed: 5 historical `PREFIX:null` rows (the junk the `build()` guard now rejects), the 3 reformatted-id twins above, and 4 whose id has since been removed from the disease. None is a loss — nobody can confirm an id the disease does not carry.
  - Disease IRIs are stable across ontology versions, so a ledger built from a newer ontology than the one a server happens to be serving stays correct: a key for an id that server does not carry simply never matches anything it renders.
- 117 tests pass (12 new, in `tests/test_id_provenance.py` and `tests/test_sssom_service.py`), ruff reports no new findings. Both features were exercised in the running app: the ∅ button toggles the cell to `∅`/"not in database" and lands in the pending drawer, and — with a stubbed signed-in user, GitHub OAuth being off locally — confirming your own id is refused with the note while another curator's id confirms normally and flagging your own still works.

## live-server-deployment-check
- Fixed the live app silently serving stale code: `deploy/update.sh` was tracked as mode `100644`, so systemd could not execute it and `ari-mm-update.service` had been failing with `status=203/EXEC` ("Failed to locate executable … Permission denied") on every 10-minute tick. The timer was enabled and firing normally the whole time, which is why nothing looked wrong from the outside. `aurint.ca/ari-editor` reported `app_version 2.126 (2026-08-11)` against `origin/main` at `2.132 (2026-08-15)` — six merged PRs, four days behind.
- `deploy/update-mappings.sh` was tracked `100644` for the same reason; both are now `100755`, matching `deploy/update-ontology.sh`, which was already `100755` and is why ontology refreshes kept working while app code and mappings did not. Mode-only change — both blob hashes are unchanged.
- The exec bit was lost because this repo's Windows clone sets `core.filemode = false`, so git records `100644` for a new script regardless of the filesystem. Add future `deploy/*.sh` with `git update-index --chmod=+x`, since a plain `chmod` will not be recorded here.
- A server-side `chmod +x` is not a durable fix and was deliberately not used: with `core.filemode` defaulting to true on Linux, the restored exec bit reads as a modification to a tracked file, so the next run of `update.sh` stashes it ([deploy/update.sh:21](deploy/update.sh:21)) and `git reset --hard` puts the mode back to `100644`. The script would disable itself again after exactly one successful update.
- Documented the failure in `DEPLOY.md` troubleshooting, including the `list-timers` + `journalctl` pair that distinguishes "timer not firing" from "timer firing, unit failing" — the logs looked identical from the app's side.
## feat-enrich-from-confirmed-xrefs
- Added an enrichment engine (`app/enrich_service.py`) that folds a disease's **confirmed** cross-references back into its own record: the matched term's label + exact synonyms extend `ARI_Synonym`, and its direct children extend `ARI_ClinicalSubtype`. Only positive (confirmed) mappings feed it; additions are de-duplicated against existing values and filtered by the synonym blocklist.
- Nothing is written implicitly. The ref-edits matrix gains an **⚗ enrichment** chip that previews the per-disease additions in a drawer (`POST /api/v2/enrichment-preview`, read-only) with an "Apply on publish" checkbox. Only then does publish send `apply_enrichment`, which applies the additions and notes them in the PR body. The chip disarms itself when the last confirmation is withdrawn, and the server recomputes the additions from the confirmed list at publish time, so the preview can never go stale.
- Built the hierarchy data: `data/2-databases/{mondo,doid,ncit}.subtypes.tsv` — one row per direct `is_a` parent→child edge (46,446 + 17,323 + 39,120), written by `scripts/fetch_databases.py` for the OBO sources. This is the `details.tsv` sidecar's hierarchy inverted: the sidecar answers "what is this term a kind of?" for a single term and keeps parent *labels* for display, while the engine asks the inverse across the whole ontology and needs *ids*, since a label does not identify a term. `_resolve_parents` now keeps the raw ids as `parent_ids` alongside the resolved labels so both readings stay available.
- **Coarse cross-references are ignored rather than trusted.** One ICD-10 code is cross-referenced by up to 134 different DOID terms; such an id identifies no single concept, yet would otherwise contribute all 134 diseases' names to one synonym list. An id ambiguous *within a source* is dropped for that source, while an id pinning exactly one term in each of several sources is kept from all of them — agreement, not ambiguity. A disease is also never proposed as its own subtype, which otherwise happened when a confirmed mapping pointed at a broader concept.
- `run.py` now honours the `PORT` environment variable (documented in `.env.example` but previously read by nothing); `--port` still overrides it. Production runs uvicorn directly and is unaffected.

## feat-ref-edits-queue-diseases
- Added the review queue to the cross-reference matrix (`/ref-edits/`), closing the gap where the per-curator queue API shipped in `feat-review-queue-api` had no frontend at all — there was no way to put a disease into anyone's queue (issue #72). Each row gets a tick box (Shift-click selects a range over the rows currently visible, so a range never reaches past an active filter), and a selection bar offers **＋ Add to my queue**; an `ASSIGN_ADMINS` member also gets a curator login + note box to queue the selection for someone else. One `POST /api/v2/assignments` covers the whole selection.
- Every row shows who holds it as an `@login` chip — tinted green when it is yours, dimmed with a ✓ once that curator has marked it done — and a new **All / My queue / Unassigned** header segment filters on it. - Fixed assignments not actually being exclusive: `owner_of` documented one owner per disease but `assign()` never checked, so the same disease could sit in two curators' queues and both would publish overlapping SSSOM rows. `assign()` now refuses a disease another curator holds unless the caller passes `reassign`, which moves it across and drops the previous owner's "done" flag for it. The refusal covers the whole call, so a partly-conflicting batch is never half-applied. The page checks its own owner map first, so the curator is asked "1 on @alice. Move them to @tester's queue?" before anything is sent — declining queues only the diseases nobody else holds.
- Tick boxes, badges and the filter render only for a signed-in curator; the anonymous page is byte-identical to before.

- Rewrote the raw HTML stored inside ontology text into markdown, completing the data half of `fix-core-js-html-escaping` below. ## fix-ref-edits-new-pr-title
- Fixed "New PR" on the cross-reference review page (`/ref-edits/`) opening a pull request titled with **every** disease reviewed in the session, including the ones already published on an earlier PR. The title (and the confirmed/flagged mappings sent with it) was rebuilt from the whole `reviewed`/`edited` state each time, and publishing never marked anything as done, so each new PR re-announced all previous work.

- The pending drawer and its chip now count unpublished verdicts only (they previously counted the whole session, so they never went down after publishing), and the Publish buttons re-enable on genuinely new work rather than on any re-render.
- Note: the ontology file itself is still committed as a whole-file snapshot of the curator's working copy, so a second PR's *diff* can include field edits already published on the first. Only the mapping files and the title are scoped per PR.

## fix-core-js-html-escaping
- Fixed `esc()` in `static/js/core.js`, the escaping helper shared by every module in the main app (194 call sites). Each mapping except the apostrophe mapped its character to **itself** — `'&':'&'`, `'<':'<'`, `'>':'>'`, `'"':'"'` — so the function escaped nothing and any markup in ontology text was injected into the DOM verbatim. The same bug was fixed in `static/ref-edits/ref-edits.js` earlier; `static/ref-curate/ref-curate.js` always had the correct version, which this now matches.
- The practical effect is that `mdToHtml()` is now actually what its comment claims — "escapes first, then formats". It was the main injection path: it runs `esc()` over a definition and then applies markdown, so with the broken helper a definition containing raw HTML was rendered as live markup.
- **Known display change:** 11 of 212 diseases have HTML tags stored *inside* their definition text (`<b>`, `<i>`, `<br>`, `<li>`, and `<a href="/Disease_Profile/….aspx">`), plus one symptom name on *Autoimmune urticaria and/or angioedema*. Those tags were rendering as live markup only because escaping was broken, and now display as literal text. Affected: Antisynthetase syndrome, Autoimmune hemolytic anemia, Autoimmune urticaria and/or angioedema, Immune thrombocytopenia, Intermediate uveitis, Juvenile Rheumatoid Arthritis, Microscopic colitis, Restless legs, Sjögren's disease, Uveitis, Warm autoimmune hemolytic anemia. The embedded `<a>` links are relative paths into a different website and already 404 from this app, so they were never working links here. Fixing the stored text is a data change for a curator, deliberately not bundled into this fix — `mdToHtml` already renders markdown, so `**bold**`, `*italic*` and `[text](https://…)` are the supported way to express this.
- Verified no double-escaping at the call sites: the five `esc()` calls that wrap link helpers (`xrefLink`, `diseaseLinkUrl`, `sub.link_iri`) pass plain URLs into `href`, where `&amp;` correctly decodes back to `&` — confirmed against a live SNOMED browser link carrying two query parameters. No disease name, synonym or definition in the ontology contains a bare `&`.

## feat-curation-matrix-ref-edits
- Rebuilt the cross-reference review page (`/ref-edits/`) on the "1c" curation-matrix design from `design/mockups/curation-matrix-1c-prototype.dc.html`. Every review database is a column and every disease one row of state glyphs, so all ten databases fit without horizontal scrolling and the page reads as a coverage map instead of a wall of id chips. Clicking a disease opens its review strip **in place** — a card per database with each id, its concept label, and ✓/✕ verdict buttons — and clicking a cell opens that mapping in the side panel as before.
- Added a per-id state model the glyphs, tints, row counts and progress all derive from: `ok` (confirmed this session or positive in the curated mappings), `bad` (flagged/negative), `pred` (exact-label prediction), `low` (synonym-only prediction), and `have` — an id on file that nobody has judged yet. `have` is new; the mockup had no state for it because its sample data treated every on-file id as already curated, but most real cells are in exactly that state. A cell only reads ✓ once every id in it has a verdict.
- Added the header controls from the design: a comfortable/compact density toggle (compact fits ~24 diseases per screen instead of 9), an explicit light/dark toggle, a `N/M diseases complete` progress bar, and a "pending" chip that opens a drawer listing this session's unpublished verdicts grouped by disease. Density and theme persist in `localStorage`.
- Concept labels for ids already on file are looked up lazily for the open row only (reusing the cached `/api/v2/concept/{db}/{id}` endpoint) and painted in place, so a card shows "alopecia totalis" rather than a bare `19754005` without blocking the render.
- Kept every existing behaviour: id editing + Save, the new-subtype overlay, session persistence, publish/New-PR, the resizable splitter and the predicted-candidate flow. The separate "discard prediction" control was folded into the ordinary ✕ verdict — both already wrote the same per-id `bad` state and published down the same negative-mapping path, so there were two controls for one action.
- Fixed `esc()` in `static/ref-edits/ref-edits.js`, which mapped `&`, `<`, `>` and `"` to themselves and so escaped nothing; ontology text containing markup was injected into the page verbatim. (`static/js/core.js` still has the identical bug and is not touched here.)
- Verdict changes re-render only the matrix, never the panel, so the source preview iframe is not reloaded underneath the curator mid-review.
- Carries forward the `fix-sssom-null-mappings` guard below: the rewritten panel renders its verdict buttons only when the cell has an id to judge, so a blank cell can still never record a review for a `null` id.
- Dropped the side-by-side ARI-vs-concept compare pane from the side panel, and merged the separate "id(s) — comma separated" edit box into the target-id block: the id now carries a ✎ that swaps it for an input over the same box (Enter saves, Esc cancels), so there is one place the id is read and written. Reclaiming both blocks gives the embedded source page enough height to actually be read. A cell with no id offers "＋ Add a … id" in the same spot. `GET /api/v2/concept/{db}/{id}` is still used for the concept labels shown under each id, so the endpoint is not now unused.
- Saving an id from the panel rewrites **only that id** and leaves the cell's other ids alone (clearing it removes it; an id not on file yet is added). The edited/verdict bookkeeping is scoped the same way, so editing one id no longer clears a verdict the curator already gave a sibling id in the same cell — the previous whole-cell save did.

## fix-sssom-null-mappings
- Fixed a curator-facing bug on the cross-reference review page (`/ref-edits`) that let a truly blank cell (no existing id, no predicted candidate) render "✓ Correct / ✗ Needs change" verdict buttons wired to a `null` id. Clicking either recorded a review for id `null`, which then published as a literal `PREFIX:null` mapping row in `ari.sssom.tsv` / `ari.equivalencies.tsv` — the source of the "nulls in the sssom files" seen on some curation PRs. The panel now shows those buttons only when the cell actually has an id to judge; a blank cell offers just the id input + Save, same as before predictions existed.
- Hardened `sssom_service.build()` (the publish-time SSSOM/equivalencies writer) at its client-input boundary: it no longer accumulates a mapping row for a blank/placeholder id (`null`/`none`/`undefined`/whitespace), and a missing disease name or ARI id now renders as an empty column instead of the literal string `"None"` (a `dict.get(key, default)` only falls back on a *missing* key, not one explicitly set to `None`).
- Added regression tests (`tests/test_sssom_service.py`) pinning both fixes.

## fix-git-permanently-dirty-worktree
- Fixed the repo permanently reporting `static/ref-edits/ref-edits.js` as modified with no edits made. The file was committed with CRLF line endings, but Git for Windows sets `core.autocrlf=true` (system gitconfig), so Git normalised the working copy back to LF on every index refresh and the result never matched the committed blob — `git checkout --` restored CRLF and the file went dirty again immediately.
- Renormalised that one file to LF (`git add --renormalize`); content is byte-identical ignoring line endings, and it is now the same LF-in-index / CRLF-in-worktree shape as every other text file here, so `git status` stays clean. No `.gitattributes` `text`/`eol` rules were added, per the note in that file.

## feat-concept-detail
- Added `GET /api/v2/concept/{db}/{id}` — label, exact synonyms, definition and parent terms for one target-database id, so the reference-review compare pane can show the candidate concept next to the ARI disease instead of just its label. The pane (in the ref-edits side panel) mirrors the two as columns and highlights the strings they share, folded the same way `predict_service` folds names so the highlighting agrees with the matcher.
- Every field is attributed to the index it came from. Only MONDO, DOID, NCIt, MeSH and Orphanet have an index of their own; SNOMED, OMOP, ICD-10, OMIM and UMLS appear only as cross-reference columns on those. So a lookup of a SNOMED/OMOP/… id returns `direct: false` with a `via` list of the hub term(s) that cross-reference it and a plain-language `note`; the pane labels that column "via MONDO" (etc.), never as the target database's own term. When several hubs claim one id their labels are all returned, and a disagreement is flagged for the curator. A valid-but-unindexed id is a normal `found: false` 200, not a 404.
- Definitions and parent terms are stored in a **sidecar** `<db>.details.tsv` (id → definition, parents) next to each index, not in the index itself: folding them in would roughly double the index size (measured 13.9 MB → 32.2 MB) and slow every prediction load for data prediction never uses. `concept_service` loads the sidecars lazily and caches them; the prediction hot path (`<db>.index.tsv`) is byte-identical to before. A missing sidecar reports `details_available: false` with a note (a checkout that never regenerated still answers with label + synonyms + provenance); a missing id within a present sidecar means the term genuinely has none. `scripts/fetch_databases.py` now also writes the sidecars, capturing OBO `def:`/`is_a:` (parents resolved to labels in a second pass, OBO qualifiers stripped), MeSH scope notes, and Orphanet definitions.
- Regenerated and committed the five detail sidecars (~18 MB total, loaded on demand); the prediction indexes are unchanged. Prediction behaviour, confidence rules and SSSOM output are unchanged — proved by a snapshot test over `predict_matches` (adding a sidecar does not alter predictions).
- Kept the lookup's memory cost proportional to use, for the small hosted instance (see `DEPLOY.md`): only the sidecar of the database actually being looked up is read (a DOID lookup holds ~8 MB resident, not the ~52 MB all five would), and the reverse id-index stores `(source, record)` tuples rather than a dict per entry (~49 MB instead of ~77 MB). Together that trims the lookup from ~129 MB to ~57 MB, all of it lazy — nothing loads until a curator opens the compare pane, so app startup is unaffected.

## feat-review-queue-api
- Added a per-curator review-queue API backing the redesigned ref-edits page: each curator works their own assigned queue of diseases one at a time instead of the full 224×10 matrix. `GET /api/v2/queue` returns the curator's assigned diseases with per-disease progress and a per-database coverage strip; `GET /api/v2/queue/{iri}` returns one disease as the review panel renders it — one entry per review database, each carrying a `status` (decided / confirmed / flagged / predicted / unreviewed / missing) the UI colours off.
- Added assignment management (`GET/POST/DELETE /api/v2/assignments`, `POST /api/v2/assignments/done`), gated by an optional `ASSIGN_ADMINS` allow-list (empty = anyone signed in).
- Decisions now autosave: every curator click posts to `POST /api/v2/decisions` (keyed per disease/database/id, so re-clicking overwrites rather than duplicating), so a reload or browser crash never loses work. `DELETE /api/v2/decisions/{id}` undoes one; `GET /api/v2/decisions` and `GET /api/v2/review-summary` show the unpublished set and the exact payload publish will send.
- Publishing falls back to the curator's autosaved decisions when the client sends none, renders them into the existing `{ari_id, iri, name, db, ids}` publish/SSSOM payload unchanged, and clears them only after the PR call succeeds — a failed publish leaves the work intact. The existing `GET /api/v2/mappings` body was lifted into a shared `_mapping_judgments()` helper with a byte-identical response.
- Added `assignments/` to `.gitignore` (runtime server-side state, same pattern as `.user-data/`).

## feat-cross-ref-manager-persistence
- The cross-reference manager (ref-edits matrix + ref-curate disease view) now saves a signed-in user's in-progress review to the server: their correct/needs-change verdicts, edited-id markers and the pull-request pointer persist per user, so a page reload resumes the work instead of losing it. State is saved automatically (debounced) on every verdict/edit and stored beside the user's working ontology copy; it is dropped when they switch source branch or their copy is swept.

- Added `.user-data/` and `.sessions.json` to `.gitignore` (runtime server-side state).
