# Changelog

## feat-ref-edits-queue-diseases
- Added the review queue to the cross-reference matrix (`/ref-edits/`), closing the gap where the per-curator queue API shipped in `feat-review-queue-api` had no frontend at all — there was no way to put a disease into anyone's queue (issue #72). Each row gets a tick box (Shift-click selects a range over the rows currently visible, so a range never reaches past an active filter), and a selection bar offers **＋ Add to my queue**; an `ASSIGN_ADMINS` member also gets a curator login + note box to queue the selection for someone else. One `POST /api/v2/assignments` covers the whole selection.
- Every row shows who holds it as an `@login` chip — tinted green when it is yours, dimmed with a ✓ once that curator has marked it done — and a new **All / My queue / Unassigned** header segment filters on it. Without that filter a curator could fill a queue but had nowhere to work it, since `/ref-curate` does not read the queue API either.
- Self-assignment is no longer gated. `ASSIGN_ADMINS` previously covered *every* assignment write, so with an allow-list configured a curator could not even claim a disease for themselves; it now restricts only assigning to (or unassigning from) **another** curator, and `login` defaults to the caller on both `POST` and `DELETE /api/v2/assignments`. `GET /api/v2/me` reports `can_assign_others` so the page knows whether to offer the curator picker instead of discovering the restriction by eating a 400.
- Fixed assignments not actually being exclusive: `owner_of` documented one owner per disease but `assign()` never checked, so the same disease could sit in two curators' queues and both would publish overlapping SSSOM rows. `assign()` now refuses a disease another curator holds unless the caller passes `reassign`, which moves it across and drops the previous owner's "done" flag for it. The refusal covers the whole call, so a partly-conflicting batch is never half-applied. The page checks its own owner map first, so the curator is asked "1 on @alice. Move them to @tester's queue?" before anything is sent — declining queues only the diseases nobody else holds.
- Tick boxes, badges and the filter render only for a signed-in curator; the anonymous page is byte-identical to before.
## fix-ontology-embedded-html
- Rewrote the raw HTML stored inside ontology text into markdown, completing the data half of `fix-core-js-html-escaping` below. That fix made `esc()` actually escape, which correctly turned these stored tags into literal visible text; this converts them to the markup `mdToHtml` supports so they render as intended again. 12 literals across 11 diseases and one symptom label, in `ontologies/ari_t1d.owl` only — 22 lines changed, no code touched.
- `<b>`/`<i>` → `**bold**`/`*italic*`, and the `<br>` + `<li>` blocks on *Juvenile Rheumatoid Arthritis* (7 subtypes) and *Microscopic colitis* (3 subtypes) → numbered markdown lists. These now render as real `<ol><li>` rather than the original `<li>` runs that had no parent list element and carried their numbering as literal text.
- Four of the twelve were **malformed** and never rendered correctly even before escaping was fixed: unclosed `<a>` tags on *Restless legs* (2) and *Sjögren's disease* (1), which swallowed the following prose into the link; crossed nesting `<i><b>genetic</i></b>` on *Immune thrombocytopenia*; and a doubly-nested `<a href="<a href="…">` on *Uveitis* whose `href` value was literally `<a href=`. There were 13 opening anchors against 10 closing ones.
- All 13 embedded `<a>` links became plain text. Each pointed at a relative `/Disease_Profile/….aspx` path on a legacy site — dead from this app — and every disease they referenced (cold agglutinin disease, paroxysmal nocturnal hemoglobinuria, uveitis, Crohn's disease, rheumatoid arthritis, Sjögren's disease, warm autoimmune hemolytic anemia, autoimmune urticaria/angioedema) already exists as its own entity here, so they were internal cross-references written as external links. `mdToHtml`'s link rule only accepts absolute `http(s)` URLs, so a relative path cannot be expressed as a markdown link regardless; substituting an invented absolute URL would have fabricated a destination none of these were verified to have.
- Edits were applied as byte-level replacements with per-pattern expected-count assertions, preserving the file's 22,567 CRLF line endings exactly (0 bare LF introduced) — this is the file called out in `fix-git-permanently-dirty-worktree` below. Verified: 0 literals containing markup remain, XML still parses (2,365 individuals), disease count unchanged at 210, 118 tests pass, and the three representative cases were confirmed in the running app — JRA renders `<ol>`/`<strong>`, *Immune thrombocytopenia* renders `<em><strong>genetic</strong></em>`, and *Restless legs* renders clean prose with zero stray anchors and no console errors.
- Fixed four prose typos in the same definitions: `can''t` → `can't` (a doubled-apostrophe escaping artifact) in *Microscopic colitis*; `IIn` → `In` and `thromocytopenic` → `thrombocytopenic` in *Immune thrombocytopenia*; `noteably` → `notably` in *Antisynthetase syndrome*. Each was verified as a single unambiguous occurrence first — the file has 6 correct `thrombocytopenic` against the one misspelling, and no other doubled apostrophe anywhere. The doubled-capital scan that caught `IIn` also matches the roman-numeral designations `IIa` and `IIb` (2 each), which are legitimate and are asserted unchanged.
- Still left for a curator, because it needs a factual decision rather than a spelling fix: the *Sjögren's disease* definition describes sicca syndrome and then says "See Sjögrens disease for more information" — a self-reference that was already circular before the dead link was removed.
## fix-ref-edits-new-pr-title
- Fixed "New PR" on the cross-reference review page (`/ref-edits/`) opening a pull request titled with **every** disease reviewed in the session, including the ones already published on an earlier PR. The title (and the confirmed/flagged mappings sent with it) was rebuilt from the whole `reviewed`/`edited` state each time, and publishing never marked anything as done, so each new PR re-announced all previous work.
- The review session now tracks what it already sent: `published[key] = {pr, state}`, saved with the rest of the session blob (`{reviewed, edited, published, branch, pr}`). A key is pending only while its current state — its verdict, plus a marker when the id was edited — differs from what was published, so changing your mind about an already-published id makes it pending again.
- The two publish buttons now mean different things, as the labels always implied. **New PR** carries only the pending keys, so its title and its SSSOM rows describe just that work. **Publish to PR #N** carries the pending keys *plus* the keys already on PR #N, because `sssom_service` rebuilds the mapping files from the base branch on every publish — the PR's earlier rows have to be re-sent or they would drop out — and its title names every disease on that PR.
- The pending drawer and its chip now count unpublished verdicts only (they previously counted the whole session, so they never went down after publishing), and the Publish buttons re-enable on genuinely new work rather than on any re-render.
- Note: the ontology file itself is still committed as a whole-file snapshot of the curator's working copy, so a second PR's *diff* can include field edits already published on the first. Only the mapping files and the title are scoped per PR.

## fix-core-js-html-escaping
- Fixed `esc()` in `static/js/core.js`, the escaping helper shared by every module in the main app (194 call sites). Each mapping except the apostrophe mapped its character to **itself** — `'&':'&'`, `'<':'<'`, `'>':'>'`, `'"':'"'` — so the function escaped nothing and any markup in ontology text was injected into the DOM verbatim. The same bug was fixed in `static/ref-edits/ref-edits.js` earlier; `static/ref-curate/ref-curate.js` always had the correct version, which this now matches.
- The practical effect is that `mdToHtml()` is now actually what its comment claims — "escapes first, then formats". It was the main injection path: it runs `esc()` over a definition and then applies markdown, so with the broken helper a definition containing raw HTML was rendered as live markup.
- **Known display change:** 11 of 212 diseases have HTML tags stored *inside* their definition text (`<b>`, `<i>`, `<br>`, `<li>`, and `<a href="/Disease_Profile/….aspx">`), plus one symptom name on *Autoimmune urticaria and/or angioedema*. Those tags were rendering as live markup only because escaping was broken, and now display as literal text. Affected: Antisynthetase syndrome, Autoimmune hemolytic anemia, Autoimmune urticaria and/or angioedema, Immune thrombocytopenia, Intermediate uveitis, Juvenile Rheumatoid Arthritis, Microscopic colitis, Restless legs, Sjögren's disease, Uveitis, Warm autoimmune hemolytic anemia. The embedded `<a>` links are relative paths into a different website and already 404 from this app, so they were never working links here. Fixing the stored text is a data change for a curator, deliberately not bundled into this fix — `mdToHtml` already renders markdown, so `**bold**`, `*italic*` and `[text](https://…)` are the supported way to express this.
- Verified no double-escaping at the call sites: the five `esc()` calls that wrap link helpers (`xrefLink`, `diseaseLinkUrl`, `sub.link_iri`) pass plain URLs into `href`, where `&amp;` correctly decodes back to `&` — confirmed against a live SNOMED browser link carrying two query parameters. No disease name, synonym or definition in the ontology contains a bare `&`.

## feat-curation-matrix-ref-edits
- Rebuilt the cross-reference review page (`/ref-edits/`) on the "1c" curation-matrix design from `design/mockups/curation-matrix-1c-prototype.dc.html`. Every review database is a column and every disease one row of state glyphs, so all ten databases fit without horizontal scrolling and the page reads as a coverage map instead of a wall of id chips. Clicking a disease opens its review strip **in place** — a card per database with each id, its concept label, and ✓/✕ verdict buttons — and clicking a cell opens that mapping in the side panel as before.
- Added a per-id state model the glyphs, tints, row counts and progress all derive from: `ok` (confirmed this session or positive in the curated mappings), `bad` (flagged/negative), `pred` (exact-label prediction), `low` (synonym-only prediction), and `have` — an id on file that nobody has judged yet. `have` is new; the mockup had no state for it because its sample data treated every on-file id as already curated, but most real cells are in exactly that state. A cell only reads ✓ once every id in it has a verdict.
- Added the header controls from the design: a comfortable/compact density toggle (compact fits ~24 diseases per screen instead of 9), an explicit light/dark toggle, a `N/M diseases complete` progress bar, and a "pending" chip that opens a drawer listing this session's unpublished verdicts grouped by disease. Density and theme persist in `localStorage`.
- Concept labels for ids already on file are looked up lazily for the open row only (reusing the cached `/api/v2/concept/{db}/{id}` endpoint) and painted in place, so a card shows "alopecia totalis" rather than a bare `19754005` without blocking the render.
- Kept every existing behaviour: id editing + Save, the new-subtype overlay, session persistence, publish/New-PR, the resizable splitter and the predicted-candidate flow. The separate "discard prediction" control was folded into the ordinary ✕ verdict — both already wrote the same per-id `bad` state and published down the same negative-mapping path, so there were two controls for one action.
- Fixed `esc()` in `static/ref-edits/ref-edits.js`, which mapped `&`, `<`, `>` and `"` to themselves and so escaped nothing; ontology text containing markup was injected into the page verbatim. (`static/js/core.js` still has the identical bug and is not touched here.)
- Verdict changes re-render only the matrix, never the panel, so the source preview iframe is not reloaded underneath the curator mid-review.
- Carries forward the `fix-sssom-null-mappings` guard below: the rewritten panel renders its verdict buttons only when the cell has an id to judge, so a blank cell can still never record a review for a `null` id.
- Dropped the side-by-side ARI-vs-concept compare pane from the side panel, and merged the separate "id(s) — comma separated" edit box into the target-id block: the id now carries a ✎ that swaps it for an input over the same box (Enter saves, Esc cancels), so there is one place the id is read and written. Reclaiming both blocks gives the embedded source page enough height to actually be read. A cell with no id offers "＋ Add a … id" in the same spot. `GET /api/v2/concept/{db}/{id}` is still used for the concept labels shown under each id, so the endpoint is not now unused.
- Saving an id from the panel rewrites **only that id** and leaves the cell's other ids alone (clearing it removes it; an id not on file yet is added). The edited/verdict bookkeeping is scoped the same way, so editing one id no longer clears a verdict the curator already gave a sibling id in the same cell — the previous whole-cell save did.

## fix-sssom-null-mappings
- Fixed a curator-facing bug on the cross-reference review page (`/ref-edits`) that let a truly blank cell (no existing id, no predicted candidate) render "✓ Correct / ✗ Needs change" verdict buttons wired to a `null` id. Clicking either recorded a review for id `null`, which then published as a literal `PREFIX:null` mapping row in `ari.sssom.tsv` / `ari.equivalencies.tsv` — the source of the "nulls in the sssom files" seen on some curation PRs. The panel now shows those buttons only when the cell actually has an id to judge; a blank cell offers just the id input + Save, same as before predictions existed.
- Hardened `sssom_service.build()` (the publish-time SSSOM/equivalencies writer) at its client-input boundary: it no longer accumulates a mapping row for a blank/placeholder id (`null`/`none`/`undefined`/whitespace), and a missing disease name or ARI id now renders as an empty column instead of the literal string `"None"` (a `dict.get(key, default)` only falls back on a *missing* key, not one explicitly set to `None`).
- Added regression tests (`tests/test_sssom_service.py`) pinning both fixes.

## fix-git-permanently-dirty-worktree
- Fixed the repo permanently reporting `static/ref-edits/ref-edits.js` as modified with no edits made. The file was committed with CRLF line endings, but Git for Windows sets `core.autocrlf=true` (system gitconfig), so Git normalised the working copy back to LF on every index refresh and the result never matched the committed blob — `git checkout --` restored CRLF and the file went dirty again immediately.
- Renormalised that one file to LF (`git add --renormalize`); content is byte-identical ignoring line endings, and it is now the same LF-in-index / CRLF-in-worktree shape as every other text file here, so `git status` stays clean. No `.gitattributes` `text`/`eol` rules were added, per the note in that file.

## feat-concept-detail
- Added `GET /api/v2/concept/{db}/{id}` — label, exact synonyms, definition and parent terms for one target-database id, so the reference-review compare pane can show the candidate concept next to the ARI disease instead of just its label. The pane (in the ref-edits side panel) mirrors the two as columns and highlights the strings they share, folded the same way `predict_service` folds names so the highlighting agrees with the matcher.
- Every field is attributed to the index it came from. Only MONDO, DOID, NCIt, MeSH and Orphanet have an index of their own; SNOMED, OMOP, ICD-10, OMIM and UMLS appear only as cross-reference columns on those. So a lookup of a SNOMED/OMOP/… id returns `direct: false` with a `via` list of the hub term(s) that cross-reference it and a plain-language `note`; the pane labels that column "via MONDO" (etc.), never as the target database's own term. When several hubs claim one id their labels are all returned, and a disagreement is flagged for the curator. A valid-but-unindexed id is a normal `found: false` 200, not a 404.
- Definitions and parent terms are stored in a **sidecar** `<db>.details.tsv` (id → definition, parents) next to each index, not in the index itself: folding them in would roughly double the index size (measured 13.9 MB → 32.2 MB) and slow every prediction load for data prediction never uses. `concept_service` loads the sidecars lazily and caches them; the prediction hot path (`<db>.index.tsv`) is byte-identical to before. A missing sidecar reports `details_available: false` with a note (a checkout that never regenerated still answers with label + synonyms + provenance); a missing id within a present sidecar means the term genuinely has none. `scripts/fetch_databases.py` now also writes the sidecars, capturing OBO `def:`/`is_a:` (parents resolved to labels in a second pass, OBO qualifiers stripped), MeSH scope notes, and Orphanet definitions.
- Regenerated and committed the five detail sidecars (~18 MB total, loaded on demand); the prediction indexes are unchanged. Prediction behaviour, confidence rules and SSSOM output are unchanged — proved by a snapshot test over `predict_matches` (adding a sidecar does not alter predictions).
- Kept the lookup's memory cost proportional to use, for the small hosted instance (see `DEPLOY.md`): only the sidecar of the database actually being looked up is read (a DOID lookup holds ~8 MB resident, not the ~52 MB all five would), and the reverse id-index stores `(source, record)` tuples rather than a dict per entry (~49 MB instead of ~77 MB). Together that trims the lookup from ~129 MB to ~57 MB, all of it lazy — nothing loads until a curator opens the compare pane, so app startup is unaffected.

## feat-review-queue-api
- Added a per-curator review-queue API backing the redesigned ref-edits page: each curator works their own assigned queue of diseases one at a time instead of the full 224×10 matrix. `GET /api/v2/queue` returns the curator's assigned diseases with per-disease progress and a per-database coverage strip; `GET /api/v2/queue/{iri}` returns one disease as the review panel renders it — one entry per review database, each carrying a `status` (decided / confirmed / flagged / predicted / unreviewed / missing) the UI colours off.
- Added assignment management (`GET/POST/DELETE /api/v2/assignments`, `POST /api/v2/assignments/done`), gated by an optional `ASSIGN_ADMINS` allow-list (empty = anyone signed in).
- Decisions now autosave: every curator click posts to `POST /api/v2/decisions` (keyed per disease/database/id, so re-clicking overwrites rather than duplicating), so a reload or browser crash never loses work. `DELETE /api/v2/decisions/{id}` undoes one; `GET /api/v2/decisions` and `GET /api/v2/review-summary` show the unpublished set and the exact payload publish will send.
- Publishing falls back to the curator's autosaved decisions when the client sends none, renders them into the existing `{ari_id, iri, name, db, ids}` publish/SSSOM payload unchanged, and clears them only after the PR call succeeds — a failed publish leaves the work intact. The existing `GET /api/v2/mappings` body was lifted into a shared `_mapping_judgments()` helper with a byte-identical response.
- Added `assignments/` to `.gitignore` (runtime server-side state, same pattern as `.user-data/`).

## feat-cross-ref-manager-persistence
- The cross-reference manager (ref-edits matrix + ref-curate disease view) now saves a signed-in user's in-progress review to the server: their correct/needs-change verdicts, edited-id markers and the pull-request pointer persist per user, so a page reload resumes the work instead of losing it. State is saved automatically (debounced) on every verdict/edit and stored beside the user's working ontology copy; it is dropped when they switch source branch or their copy is swept.
- Publishing now offers a choice once a PR exists: the primary button commits to the current PR, and a new "New PR" button opens a fresh pull request instead. The PR pointer is restored on reload so "Publish to PR #N" survives a refresh.
- Added `.user-data/` and `.sessions.json` to `.gitignore` (runtime server-side state).
